# 5. נתונים, אלגוריתם ותקינות חוקים

## טיפוסי נתונים מומלצים (TypeScript, להתאמה לסטאק קיים)

```ts
type GameScenario = {
  id: string;
  version: number;
  kind: 'fictional' | 'historical';
  title: string;
  targetSeats: 61;
  totalSeats: 120;
  timeLimitSeconds: number;
  cards: Array<{ id: string; nameHe: string; seats: number; color: string }>;
  rules: { exactTarget: boolean; maxCards?: number };
  sourceUrl?: string; // required for historical scenarios
  sourceDate?: string;
};

type CompletedRun = {
  scenarioId: string;
  scenarioVersion: number;
  selectedCardIds: string[];
  resultSeats: number;
  elapsedMs: number;
  completed: boolean;
  recordedAt: string;
};
```

## דרישות לאלגוריתם

- `sum(cards.map(c => c.seats)) === 120` לכל תרחיש סטנדרטי.
- במצב הרגיל, ניצחון רק כשהסכום **בדיוק 61** ולא מעל.
- אתגר חייב להיות פתיר: בדיקה ב־backtracking או דינמיקה לפני פרסום; במצב של `maxCards`, לוודא שיש פתרון שגם עומד במגבלה.
- בדיקות יחידה: סכום נתונים, פתרון תקין, אי־קבלת 62, זיהוי חוסר פתרון, ריסט, שינוי גרסת אתגר, ומעבר חצות בישראל.
- האתגר היומי יהיה דטרמיניסטי: לפי `YYYY-MM-DD` ב־`Asia/Jerusalem` + גרסת סט תרחישים, כדי שחברים יקבלו **אותו אתגר**. אם משנים תוכן באמצע היום, לשמור גרסה קיימת ולא לשבור קישורים.
- הטיימר מתחיל רק בלחיצת ״התחל״ לאחר שכל הגרפיקה החיונית נטענה; אפשר להציג 3...2...1 קצר, עם אפשרות דילוג. לא להעניש על זמני טעינה.
- להשתמש ב־`performance.now()` בצד לקוח למדידה חזותית, ולצד שרת לאימות תוצאות ל־Leaderboard. אין להאמין ל־elapsedMs שנשלח מהלקוח לבדו.
- בתרחישים היסטוריים: מאגר מאומת ממקור רשמי, תאריך, רשימת סיעות ותוצאות, ללא השלמת מושבים או טענות שלא נבדקו. מצב היסטורי אינו חייב להיות ב־MVP.

# 6. היבטים טכניים

**כלל עליון:** השתלב בקוד הקיים אם הוא נמסר. אל תייצר מחדש את כל האתר בלי צורך.

## אם מתחילים מפרויקט חדש

- Frontend: React + TypeScript. לפרויקט עצמאי שהופך לאתר מלא עם נתיבים ו־OG בשרת: Next.js App Router או פתרון שקול לפי סביבת הפריסה.
- Styling: CSS Modules או Tailwind לפי הקיים, עם design tokens במקום צבעים קשיחים בכל רכיב.
- Animations: Motion/Framer Motion אם כבר מותקן ותואם; אחרת CSS transitions ו־SVG מתון כדי לצמצם תלות.
- Icons: SVG מקוריים או Lucide.
- MVP ראשוני ללא DB: תרחישים JSON, שמירת העדפות מקומיות ורצף משחק במכשיר רק לפי צורך ובהתאם למדיניות פרטיות. בלי דירוג מזויף.
- שלב הרחבה: שרת/DB קטן (למשל Supabase או DB קיים), API לתוצאות, אימות אתגר וקצב פניות, בלי לאחסן נתוני הצבעה אישיים.
- פריסה: לפי ספק האירוח הקיים, עם תמיכה ב־HTTPS, פריסה ובדיקת preview לפני production.

## ביצועים, נגישות ו־SEO

- עמוד כניסה חייב לכלול HTML שרת/סטטי עם `title`, `description`, `canonical`, H1, FAQ קצר וטקסט שמסביר את המשחק; לא להסתפק בקנבס שאי אפשר לאנדקס.
- Open Graph ו־Twitter Card תקינים לכתובת האתגר ולכתובת ברירת המחדל.
- `robots.txt` ו־`sitemap.xml` בהתאם לארכיטקטורה הקיימת.
- Lazy load לאנימציות כבדות; אין להשתמש בסרטון כבד אוטומטי מעל לקפל.
- תמיכה במקלדת, focus ברור, `aria-label` לכרטיסים ומצב בחירה, הודעות חיות לקוראי מסך ללא הצפה.
- לבדוק 360px, 390px, 430px ו־Desktop; Safari iOS, Chrome Android ו־Chrome Desktop.
- תיעוד `dir="rtl"` ברמת אזור המשחק, ו־`lang="he"`.
- יעד איכות: Lighthouse mobile performance גבוה ככל האפשר, בלי להפוך מספר יחיד לתחליף לבדיקת שימוש אמיתית.

## פרטיות והגינות

- לא לדרוש הרשמה או מספר טלפון כדי לשחק או לשתף.
- לא לאסוף העדפות פוליטיות. אל תציג בחירת כרטיסים דמיוניים כאינדיקציה להצבעה אמיתית.
- מדידות: אירועים מצטברים כגון `game_started`, `game_completed`, `share_clicked`, `retry_clicked`, `daily_return` בלבד, בכפוף למימוש פרטיות ותנאי האנליטיקה של האתר.
- אם מתווסף Leaderboard, כינויים בדויים, יכולת דיווח, rate limiting, בדיקת ביצועים מזויפים ותנאים ברורים.
- אם האתר עובר לבעלות חדשה, יש להציג גילוי נאות מעודכן ולבחון את השלכות הפרטיות והדין בנפרד.
